# Global Rules

## 書き方（最重要）

**わかりやすさが最優先。必要な情報だけに削ぎ落とし、図と表で理解させる。**

- **削ぎ落とす**: 調べたデータは 9 割捨てる。「これが無いと読み手が判断できないか」だけが載せる基準
- **図と表にする**: 処理の流れは mermaid、数字や選択肢の比較は表。地の文で経路を追ったり内訳を並べたりしない
- **平易に書く**: 読み手はそのコードを書いた人ではない
  - **関数名・メソッド名・型名は地の文に出さない。出すのは図の中だけ**
  - 専門用語・内部用語も避ける（❌ ack/nack, early return, 冪等, 索引, 伝播, 排他的 → ✅「成功したことになる」「何度もやり直される」「検索用のデータ」）
  - 残してよい固有名詞は読み手が日常的に見ているものだけ（Pod 名・環境変数名・クラスタ名・監視ツール名）
- **分量**: チャットは結論 3-5 行 + 表 1 つ。Issue / PR コメントは 1 スクロールで読み切れる長さ（節は 3 つまで、表は 1 節に 1 つ）。超えそうなら先に「ここまでで良いか」を聞く

やらないこと: コマンド出力や中間データの貼り付け／手順・クエリ・パラメータの詳細／同じ数字を表と地の文の両方に／網羅性のアピール／完了報告での本文再掲（リンク + 一行要約だけ）。

禁止表現: 比喩（「幽霊ドキュメント」等）、曖昧な言い回し（「意図的な設計」等）、「仕様どおり」だけで済ませる結論。

深掘りする前に結論を数行出して粒度を確認する。詳細が必要になったら本文を膨らませず Artifact に出す（「詳細な調査結果は Artifact に出す」参照）。

## 調査メモ（Issue コメント）の型

手本: [wantedly/infrastructure#15966](https://github.com/wantedly/infrastructure/issues/15966#issuecomment-5393003865)

1. 見出しは `## 📝 調査メモ`
2. 冒頭に**リスクを箇条書き**で並べる。ネストで影響を展開する。「結論」の節は立てない
3. 「そのため、〜を考える」の 1 文で目的を書く
4. `### 前提` — 判断の土台になる事実だけ。主張ごとに `([該当コード](permalink))` をインラインで貼る
5. **mermaid の図**で処理の流れを示す
6. `### 影響` — 表 1 つ（`影響 / 内容 / 検知`）
7. `### 対策案` — 表 1 つ（`案 / 内容 / 戻し方`）。追加提案は `+α として、〜したい` で 1 段落

常体（だ・である調）で書く。絵文字は見出しの `📝` だけで、重要度マークや `C1` `W3` のような独自ラベルは振らない。章末にまとめを再掲しない。

## mermaid

- 「処理の流れ」と「失敗したときにどこで止まるか」を 1 枚に収める。正常系だけの図は描かない
- 関数名を出してよいのは図の中だけ。ここで技術的な詳細を引き受けて地の文を平易に保つ
- `flowchart TB` を基本に。ラベルは `"..."` で囲み改行は `<br/>`。分岐は `-->|成功|` / `-->|"失敗 → 処理を終了 (return nil)"|`
- 失敗経路だけ赤系（`fill:#ffe0e0,stroke:#d04040`）、通常の処理は青系（`fill:#e8f0fe,stroke:#5b7fc4`）を `classDef` で当てる

## PR / Issue

- Why（なぜ必要か）/ What（何をするか）形式。Why は 2-3 文、What は 1 項目 1 行
- 関連 Issue は `- https://github.com/org/repo/issues/123` の形式で書く（GitHub がタイトルを表示してくれる）
- 詳細な背景・調査経緯は Issue 側に書き、PR からはリンクで参照する
- コードへの参照は commit hash 固定の permalink（`.../blob/<commit-hash>/path#Lx-Ly`）。コードの抜粋や `file.go:107-109` のような相対行番号は使わない
- **既存コメントを編集するときは必ず最新本文を取得してから差分だけ直す。** 全文の上書きは、ユーザーが後から追記した内容を消すので禁止
- 他人が書いたコメントは上書きしない

## Git

- 作業前に `git fetch` / `git pull` で最新化する
- 新しいブランチは必ずデフォルトブランチから切る（`master` か `main` かはリポジトリごとに確認）。ブランチ名は `kkato/<name>`
- 既存の作業ブランチにいても、別目的の変更は新しいブランチを切って行う
- `git add -A` / `git add .` は使わない。ファイルかディレクトリを明示する

## 環境

- リポジトリは ghq 管理（`~/ghq/github.com/<org>/<repo>`）。clone せずこのパスを使う
- 一時ファイルは `/tmp` ではなく `~/tmp`
- `kubectl` ではなく `kube <env> <サブコマンド>`（env は `sandbox`/`sb`, `qa`, `production`/`prod`）
- 略称: wtd/wtd → wantedly/wantedly
- CLAUDE.md・settings.json・hooks・skills・codex の config.toml は `~/ghq/github.com/kkato/dotfiles` で管理。plugin/skill を入れるときは dotfiles 側を編集して commit・push する（その場で `claude plugin install` して終わりにしない）

## 詳細な調査結果は Artifact に出す

**Issue コメントは削ぎ落とした結論、Artifact は根拠を含む詳細版**という使い分けにする。詳細な調査結果や比較検討が必要になったら、チャットや Issue コメントを膨らませるのではなく HTML を作って Claude Code の Artifact として publish する。

- Artifact に publish して URL を返す。チャット側は結論 1-2 行 + URL だけ
- Artifact が使えない環境では `~/tmp/<slug>.html` に出して `open` でブラウザで開く（対象リポジトリ内には置かない）。この場合のみ mermaid を CDN から読み込む（`https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs`）。Artifact は `<pre class="mermaid">` をネイティブ描画するので CDN 読み込み不要
- **視覚的にわかりやすくする**: 処理の流れは mermaid、数字や選択肢の比較は表、構成の説明は図。地の文を長く続けない
- 構成は「結論（数行）→ 図で全体像 → 表で内訳 → 解釈」。節ごとに図か表を 1 つ持たせる
- ユーザーは読んでチャットで質問してくる。指摘されたら該当箇所の差分だけ直して同じファイルを再 publish する（同じ URL が更新される）。全文の書き直しはしない

## Plan mode

- 結論と変更内容だけ書く。調査の経緯や選択肢の比較は書かない。Context は 2-3 行
